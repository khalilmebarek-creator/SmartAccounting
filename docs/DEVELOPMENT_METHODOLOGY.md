## 1. نظرة عامة — منهجية العمل الفعلية

يُطوَّر المنتج وفق **نموذج تكراري موجّه بالأهداف (Goal-Driven Iterative Model)** بعناصر من Scrum:

- **وحدة العمل = "جلسة" (Session)**: لكل جلسة هدف محدد، ملفات متأثرة، ونتيجة قابلة للتحقق (عدد اختبارات/تغطية/سلوك).
- كل جلسة تُسجَّل في `PROJECT_MAP.md` EXECUTION LOG برمز الحالة (✅ ناجح / 🔶 جزئي / ⛔ فاشل).
- كل جلسة تُنهى بـ **commit** واحد أو أكثر بأسلوب Conventional Commits.
- الدليل على التكرار والانضباط: 70+ commit على main بين 2026-07-27 و2026-08-04، كلها مرتّبة (`feat/fix/docs/test/refactor/ci/chore`).

## 2. الأدوار والمسؤوليات (بند 5.3/7.1)

| الدور | المسؤولية في هذه الجلسة |
|-------|--------------------------|
| مدير المشروع | تحديد الأهداف، أولوية الميزات، اعتماد الإصدارات، إدارة المخاطر |
| المطوّر (Staff) | التصميم والتنفيذ وفق بروتوكول "التعديل الجراحي" (AGENTS.md) — لا يُمسّ إلا ما يخص الهدف |
| مهندس ضمان الجودة (QA) | كتابة الاختبارات أولاً (TDD)، تشغيل المجموعة الكاملة، تغطية الوحدات، مراقبة CI |
| موثّق | صيانة PROJECT_MAP + AGENTS + docs/ (الموقع) + CHANGELOG بعد كل جلسة |

> في مرحلة الإعداد المبكرة قد تتعدد الأدوار على شخص واحد — المسؤولية الموثقة تبقى إلزامية.

## 3. دورة حياة الميزة (Flow of a Feature — بند 8.3)

```
الفكرة/طلب المستخدم
      │
      ▼
[1] تحليل التأثير (Impact Analysis)  ← قراءة PROJECT_MAP + تحديد الملفات المتأثرة
      │
      ▼
[2] تصميم (DRY + طبقة Shared/Core + Logging)
      │
      ▼
[3] الكتابة ببروتوكول التعديل الجراحي (AGENTS.md):
    • المس فقط ما يجب لمسه · مطابقة أسلوب الكود الحالي · تنظيف مخلفاتك فقط
      │
      ▼
[4] اختبار TDD: كتابة الاختبار ← تأكيد فشله ← جعله ينجح ← عدم كسر القديم
      │
      ▼
[5] تشغيل المجموعة الكاملة: python -m pytest tests -q
      │
      ▼
[6] تحديث التوثيق: USER_GUIDE / KNOWLEDGE_BASE / API_REFERENCE / الموقع (docs/)
      │
      ▼
[7] مزامنة الحالة: PROJECT_MAP.md (سطر EXECUTION LOG) + AGENTS.md
      │
      ▼
[8] Commit بأسلوب Conventional Commits + push → CI
```

## 4. الرقابة على التطوير والاختبار (بند 8.3.4/8.3.5)

| مرحلة النشاط | المراقبة | المقياس الحالي |
|--------------|----------|----------------|
| الصحة الوظيفية | `python -m pytest tests -q` | **1800/1800 ناجح** (62 ملفًا) |
| تغطية الوحدات | `coverage run --source=modules` | **100%** (0 مفقود) |
| أداء الإقلاع | `tests/test_startup_perf.py` | 44ms (الحد المسموح ≤3s) |
| أداء المشاهد | نفس الملف (95–402ms) | الحد المسموح ≤1.5s |
| استقرار الذاكرة | نفس الملف | 45MB (الحد المسموح ≤700MB) |
| توقع الانحدار | CI في GitHub Actions عند كل push إلى main | أخضر (1800 passed, 27.8s) |

معايير القبول (Definition of Done):
1. المجموعة الكاملة 1800 اختباراً ناجحة.
2. تغطية وحدات 100%.
3. لا تسريب لأسرار/بيانات حالة في git.
4. التوثيق محدّث + سطر EXECUTION LOG مضافة.
5. لا انحدار في الأداء (ضمن الحدود المتسامحة).

## 5. عدم المطابقة والإجراءات التصحيحية (بند 10.2)

لكل خطأ مكتشف أثناء التطوير أو اختبارات التكامل أو ملاحظات المستخدم:

```
مكتشف الخطأ
   │
   ▼
Root Cause (الجذر) ← توثيق في PROJECT_MAP.md "جداول الأخطاء"
   │
   ▼
الإصلاح ببروتوكول جراحي (لا يُلمّس إلا المتأثر)
   │
   ▼
اختبار انحدار (Regression Test) يضمن عدم تكراره
   │
   ▼
تسجيل في EXECUTION LOG + (إن استلزم) تحديث CHANGELOG
```

**أمثلة موثقة فعلية:**
- بغّ تبديل اللغة (طلب `_clear_layout` غير موجود) → إصلاح + 5 اختبارات انحدار
- بغّ ألوان جدول المعاملات في المزامنة البنكية → إصلاح + اختبار
- 13 خللاً في إصدار + مراجعة أمان شاملة → كل خَلل بجدول جذر/إصلاح/اختبار
- 3 أخطاء منتج كشفها اختبار التكامل (رأس المال العامل / حذف notas / نسخ WAL)

## 6. إدارة التكوين والإصدارات (بند 7.5/8.5.2)

### 6.1 التحكم في الشيفرة (Configuration Management)
- **Git** هو نظام التحكم المرجعي (رئيس `main` + وسوم إصدارات).
- Convention: `feat:` / `fix:` / `docs:` / `test:` / `refactor:` / `ci:` / `chore:`.
- `.gitignore` يحجب ملفات الحالة والأسرار (`users.json`, `*.db`, `.vault_salt`, `logs/`…) — **0 ملف حساس متعقَّب (تحقق 2026-08-04)**.

### 6.2 دورة الإصدار (Release — بند 8.5)
```
bump config.py + i18n window_title + installer.iss + build_nuitka.py
      → تحديث docs/version.json (changelog + URLs)
      → تحديث docs/index.html + script.js (3 لغات) + README badge
      → إعادة بناء Nuitka → Inno Setup → ZIP محمول
      → وسم git (vX.Y.Z) + GitHub Release بأحدث assets
      → تحديث AGENTS.md + CHANGELOG.md (+ توثيق أي شذوذ مثل v3.1.5)
```

**قاعدة الرفع (تعميل فعلي):** *"بعد كل تعديل كود، تحديث الموقع (docs/) مطلوب — بعد كل تعديل، تحديث PROJECT_MAP.md مطلوب"* (AGENTS.md).

### 6.3 تتبع الإصدارات (Traceability)
- كل إصدار منشور له وسم git + إدخال في `CHANGELOG.md` + صف في EXECUTION LOG.
- شذوذ v3.1.5 (بلا commit مستقل — دُمج في a2e6cd2) **موثّق صراحة** في CHANGELOG بدل التظاهر بوجوده.

## 7. إدارة المخاطر (بند 6.1 — يُكمّل QUALITY_POLICY.md)
انظر سجل المخاطر في `docs/QUALITY_POLICY.md` (CI/توحيد الإصدارات/الوسوم/فقدان بيانات الترقية). تُحدَّث عند كل إصدار رئيسي.

## 8. تحسين مستمر (بند 10.3)
- مراجعة دورية لجداول الأخطاء + أهداف الجودة (9 أهداف قابلة للقياس في QUALITY_POLICY).
- كل جلسة "ملاحظات مستخدم" تعالج ملاحظة حقيقية تفسر إلى تغيير مُوثَّق (أمثلة جلسات 2026-08-02/03/04).
- مؤشر "وقت المجموعة الكاملة" مراقَب (39–41s محلياً / 28s على CI) كمعرض الصحة.
